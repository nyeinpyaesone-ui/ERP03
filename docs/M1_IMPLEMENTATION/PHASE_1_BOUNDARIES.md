## Objective
Define clear business domain boundaries and use-case separation.

## Status
- [ ] Core business domains defined

## Core Business Domains

### Domain 1: Master Data Management
**Responsibility:** System of record for all static reference data

```yaml
domain_name: Master Data Management
owner: Foundation Module
core_entities:
  - Company
  - Chart of Accounts
  - Customer (master record)
  - Supplier (master record)
  - Product/SKU (master record)
  - Warehouse/Location (master record)
  - Employee (master record)
  - Tax Codes

data_ownership:
  - Company: Created/updated by system admin
  - Customer: Owned by Sales module (with Finance read)
  - Product: Owned by Inventory/Procurement
  - Warehouse: Owned by Inventory
  - Employee: Owned by HR

read_permissions: ALL modules
write_permissions: SPECIFIC (owner module only)
modification_frequency: "Low (change control required)"

use_cases:
  - Create Company (admin only)
  - Create/Update Customer Master (sales team)
  - Create/Update Product Master (procurement/inventory team)
  - Activate/Deactivate Master Records (owner + approval)
```

### Domain 2: Financial Transactions
**Responsibility:** All monetary movements and financial records

```yaml
domain_name: Financial Transactions
owner: Finance Module
core_entities:
  - Invoice
  - Purchase Order
  - Payment
  - Journal Entry
  - General Ledger Entry
  - Tax Calculation
  - Bank Reconciliation

data_ownership:
  - Invoice: Created by Sales/Procurement, finalized by Finance
  - Payment: Owned by Finance
  - Journal Entry: Owned by Finance (audit required)
  - GL Entry: System-generated by Finance

read_permissions: Finance, Sales, Procurement, HR, Analytics
write_permissions: Finance only (Sales/Procurement create documents)
modification_frequency: "Medium (requires audit trail)"
modification_constraints:
  - No deletion of GL entries (only reversal)
  - Posted documents cannot be modified
  - Lock period enforced (e.g., no modifications after month close)

use_cases:
  - Create Invoice (Sales)
  - Create Purchase Order (Procurement)
  - Record Payment (Finance)
  - Close Period (Finance)
  - Reverse Posted Entry (Finance + Approval)
  - Generate Financial Reports (Finance/Analytics)
```

### Domain 3: Inventory Management
**Responsibility:** Physical stock tracking and warehouse operations

```yaml
domain_name: Inventory Management
owner: Inventory Module
core_entities:
  - Stock Level
  - Stock Movement
  - Shipment
  - Receipt
  - Warehouse Location
  - Lot/Serial Number
  - Reorder Point

data_ownership:
  - Stock Level: System of record in Inventory
  - Stock Movement: Created by Inventory transactions
  - Shipment: Created by Sales fulfillment
  - Receipt: Created by Procurement receiving

read_permissions: Inventory, Sales, Procurement, Finance, Analytics
write_permissions: Inventory only
modification_frequency: "High (real-time)"
modification_constraints:
  - No negative stock (except reservations)
  - Movement must include reason/reference
  - Lot tracking required for regulated items

use_cases:
  - Adjust Stock (inventory team)
  - Reserve Stock (sales order)
  - Ship Order (warehouse)
  - Receive Purchase (receiving dock)
  - Count/Reconcile Inventory (inventory team)
  - Generate Stock Reports (Inventory/Analytics)
```

### Domain 4: Sales & Orders
**Responsibility:** Customer interactions and order fulfillment pipeline

```yaml
domain_name: Sales & Orders
owner: Sales Module
core_entities:
  - Customer
  - Sales Order
  - Sales Order Line
  - Quote
  - Opportunity
  - Activity
  - Invoice

data_ownership:
  - Customer: Master in Sales (updated from other modules with approval)
  - Sales Order: Created and owned by Sales
  - Quote: Created and owned by Sales
  - Invoice: References SO, owned by Finance

read_permissions: Sales, Finance, Inventory, Logistics, Analytics
write_permissions: Sales primarily
modification_frequency: "Medium"
modification_constraints:
  - Quote valid for 30 days
  - Cannot modify SO after shipment (only cancel/return)
  - Customer hold prevents new orders

use_cases:
  - Create Quote (sales rep)
  - Convert Quote to Order (sales rep)
  - Approve Large Order (sales manager)
  - Release Order for Fulfillment (sales)
  - Record Payment (customer service)
  - Generate Sales Reports (Sales/Analytics)
```

### Domain 5: Procurement & Suppliers
**Responsibility:** Purchasing and vendor management

```yaml
domain_name: Procurement
owner: Procurement Module
core_entities:
  - Supplier
  - Purchase Order
  - Purchase Order Line
  - RFQ (Request for Quote)
  - Receipt
  - Invoice Match (3-way match)
  - Supplier Performance

data_ownership:
  - Supplier: Master data
  - Purchase Order: Created and owned by Procurement
  - Receipt: Created by Inventory (receiving)
  - Invoice Match: Owned by Finance

read_permissions: Procurement, Finance, Inventory, Analytics
write_permissions: Procurement (PO), Inventory (Receipt), Finance (Invoice Match)
modification_frequency: "Medium"
modification_constraints:
  - Cannot modify PO after receipt
  - Receipt triggers inventory and finance processes
  - Invoice match required before payment

use_cases:
  - Create RFQ (procurement team)
  - Create Purchase Order (procurement team)
  - Receive Goods (warehouse)
  - Match Invoice (finance team)
  - Process Payment (finance team)
```

### Domain 6: Human Resources & Payroll
**Responsibility:** Employee data and compensation

```yaml
domain_name: Human Resources
owner: HR Module
core_entities:
  - Employee
  - Department
  - Position
  - Payroll Record
  - Leave Request
  - Expense Report
  - Performance Record

data_ownership:
  - Employee: Master in HR
  - Payroll: Created by HR/Payroll
  - Leave: Managed by HR
  - Expense: Created by Employee, approved by Manager/Finance

read_permissions: HR, Finance, Analytics
write_permissions: HR (employee data), Payroll (payroll), Employee (self-service)
modification_frequency: "Low (employee data), High (payroll)"
modification_constraints:
  - Sensitive data access restricted
  - Payroll changes require approval
  - Historical data immutable

use_cases:
  - Onboard Employee (HR)
  - Update Employee Info (HR/self-service)
  - Create Payroll (payroll team)
  - Process Leave Request (manager approval)
  - Expense Reimbursement (employee/manager/finance)
```

## Use-Case Flow Examples

### Use-Case: Complete Sales Order Flow

```
┌─────────────────────────────────────────────────────────────────┐
│ Sales Module (Primary)                                          │
├─────────────────────────────────────────────────────────────────┤
1. Create Sales Order
   - Validate Customer (master data)
   - Validate Product (master data)
   - Create SO header + lines
   - IDEMPOTENCY KEY required
   - AUDIT: Who, when, what
   └─────────────┬─────────────┘
                 │
                 ↓
2. Inventory Reservation (Inventory Module)
   - Reserve stock for each line
   - Create reservation record
   - ATOMIC transaction with SO creation
   - FAIL: Return error, rollback SO
   └─────────────┬─────────────┘
                 │
                 ↓
3. Release for Fulfillment (Warehouse)
   - Pick items from warehouse
   - Create shipment
   - Update stock deduction
   └─────────────┬─────────────┘
                 │
                 ↓
4. Create Invoice (Finance/Sales)
   - Reference SO
   - Create invoice lines
   - Calculate taxes
   - Finance takes ownership
   └─────────────┬─────────────┘
                 │
                 ↓
5. Receive Payment (Finance)
   - Link payment to invoice
   - Reconcile with accounting
   - Update GL
   - AUDIT TRAIL complete
   └─────────────┬─────────────┘
                 │
                 ↓
  ✓ COMPLETE: SO fully processed
```

### Boundary Violations (PREVENT THESE)

```yaml
Boundary Violations:
  1. Sales directly modifying inventory (WRONG)
     Correct: Sales creates order, Inventory updates stock
  
  2. Inventory directly posting GL entries (WRONG)
     Correct: Inventory records movement, Finance generates GL entry
  
  3. Bypassing finance for expense approval (WRONG)
     Correct: Employee submits, Manager approves, Finance processes
  
  4. Multiple modules updating same master record (WRONG)
     Correct: Single owner module, others request changes
  
  5. Circular dependencies (WRONG)
     Correct: Clear hierarchical data flow
```

## Domain Interaction Matrix

```
             | Finance | Inventory | Sales | Procurement | HR
-------------|---------|-----------|-------|-------------|-----
Finance      |    -    |     W     |   W   |      W      |  W
Inventory    |    R    |     -     |   W   |      W      |  -
Sales        |    R    |     R     |   -   |      R      |  -
Procurement  |    R    |     W     |   R   |      -      |  -
HR           |    R    |     -     |   R   |      R      |  -

W = Write permission (can modify)
R = Read permission only
-  = No interaction
```
